💾_SaveSystem - Intercepteurs de données - Documentation

Module Système de Sauvegarde : écrire et relire les données d'un système de jeu dans un fichier JSON, chiffré ou non, et relier ces données aux propriétés d'un nœud.

Godot 4.7+ Bibliothèque bin/save_system 6 classes JSON · AES-256

📝 Présentation

Sauvegarder l'or du joueur, ses options ou les coffres déjà ouverts demande toujours les mêmes étapes : choisir un dossier, nommer le fichier, convertir les valeurs en texte, éventuellement brouiller le fichier pour décourager la triche, puis faire l'inverse au chargement — et recommencer pour chaque système du jeu. Ce module regroupe ces étapes : une ressource SaveData par système (« joueur », « options », « monde »), une ligne pour l'écrire ou la relire, et un nœud qui recopie automatiquement des propriétés choisies.

🗃️ SaveData + SaveConfig

Ce qu'on sauvegarde (un dictionnaire, un identifiant qui donne le nom du fichier) et où (dossier, extensions), avec ou sans chiffrement.

💾 SaveManager

Le point d'entrée : save, load, delete, avec un message dans la console à chaque opération.

🔗 SaveDataBinder

Un nœud qui sauvegarde et restaure des propriétés d'un nœud ou d'une ressource (« pv », « or », « niveau ») sans écrire de code de conversion.

⚙️ SaveFileAccess · SaveSerializer

Les étages bas niveau (fichier + chiffrement, JSON), utilisables seuls pour un besoin particulier.

Pour qui ? Les développeurs qui veulent une sauvegarde simple par système de jeu, et les game designers qui choisissent, dans l'inspecteur d'un SaveDataBinder, quelles propriétés d'un objet doivent survivre à la fermeture du jeu.

Ce que ce module n'est pas
  • Pas un sérialiseur de scène : il ne sauvegarde ni nœuds, ni ressources, ni objets ; seulement des valeurs simples (nombres, textes, booléens, tableaux et dictionnaires de ces types). Un Vector2 ou une Color doivent être décomposés (voir limitations).
  • Pas une protection sérieuse contre la triche : le chiffrement décourage l'édition du fichier à la main, il ne résiste pas à quelqu'un de motivé.
  • Pas un gestionnaire d'emplacements : plusieurs parties s'obtiennent en changeant le dossier de la SaveConfig ; aucune liste, date ou miniature n'est gérée.
  • Les contrôles du joueur se sauvegardent avec PlayerInput.save_bindings (module 🕹️ Entrées de périphérique), indépendant de ce module.

Mise en place

  1. Compiler le module (si les binaires ne sont pas déjà présents) depuis la racine du dépôt : 
    scons save_system
    son registre est save_system_register.cpp : seule cette bibliothèque est compilée, et son .gdextension régénéré.
  2. Copier le dossier bin/save_system/ dans le projet Godot, au même emplacement : res://bin/save_system/.
    le .gdextension référence ses binaires par des chemins res://bin/save_system/….
  3. Redémarrer l'éditeur après le premier ajout.
    Godot ne découvre les extensions qu'au démarrage ; ensuite, elles sont rechargées à chaud (reloadable = true).
  4. Changer la clé de chiffrement par défaut de vos SaveData (32 caractères, propriété encryption_key).
    la clé par défaut, REMPLACER_PAR_UNE_CLE_SECRETE_32, est la même pour tous les projets qui utilisent ce module : un fichier chiffré avec elle est lisible par n'importe qui.
  5. Vérifier : Ajouter un nœud propose SaveDataBinder, Nouvelle ressource… propose SaveData et SaveConfig. Au lancement, la console affiche « 💾Module de sauvegarde et de debug chargé avec succès ! » (les émojis de ce message peuvent s'afficher mal, sans conséquence).
    si les classes manquent, la bibliothèque n'est pas chargée : voir l'erreur dans le panneau Sortie.

Aucun autoload n'est requis : SaveManager, SaveFileAccess et SaveSerializer sont des classes statiques, appelées directement par leur nom.

⚙️ Mode d'emploi

Objectif : conserver l'or et les PV du joueur d'une session à l'autre, sans code de conversion.

  1. Dans le script du joueur, déclarer des propriétés simples : 
    extends CharacterBody2D
var pv := 100
var piece_or := 0
    le binder lit et écrit des propriétés par leur nom ; nombres, textes et booléens survivent tels quels au passage par JSON.
  2. Ajouter un nœud SaveDataBinder dans la scène, et régler node_target sur le joueur.
    c'est la cible dont les propriétés seront lues à la sauvegarde et réécrites au chargement.
  3. Créer son save_data (Nouveau SaveData) et régler system_id = joueur et une encryption_key de 32 caractères.
    system_id donne le nom du fichier : user://saves/joueur.sav (chiffré par défaut). Le dossier vient de la file_config, créée automatiquement.
  4. Lister les propriétés suivies : tracked_properties = pv, piece_or.
    seules ces propriétés sont écrites et restaurées.
  5. Charger au démarrage, sauvegarder à la fermeture : 
    # Script de la scène principale
func _ready() -> void:
	$SaveDataBinder.load() # sans fichier : rien ne change

func _notification(what: int) -> void:
	if what == NOTIFICATION_WM_CLOSE_REQUEST:
		$SaveDataBinder.save()
    load relit le fichier et réapplique les valeurs ; save relit les propriétés puis écrit le fichier. La console confirme chaque sauvegarde.

💻 API Accessible

Référence générée depuis doc_classes/SaveManager.xml, SaveData.xml, SaveDataBinder.xml, SaveConfig.xml, SaveFileAccess.xml et SaveSerializer.xml.

Référence XML en retard sur le code

Les XML de SaveManager, SaveData et SaveConfig ont été générés avant leurs derniers changements et doivent être régénérés (scons gen_doc) ; les descriptions rédigées seront conservées. En attendant :

  • SaveManager.load(save_data, config) renvoie un SaveData (le tableau affiche void et aucun paramètre) ; save(save_data, config) prend aussi ces deux paramètres ; SaveManager.delete(save_data, config) existe mais n'apparaît pas.
  • SaveData expose aussi ses valeurs comme propriétés (system_id, data, is_encrypted, encryption_key, file_config), et SaveConfig les siennes (save_directory, extension, encrypted_extension) : seuls leurs accesseurs figurent dans les tableaux.

Internes, non exposés : le chiffrement (pad_key, generate_iv, encrypt, decrypt) et le calcul du chemin (get_path, ensure_directory_exists) de SaveFileAccess ; la résolution de la cible du binder (get_target, identifiant d'instance du nœud cible).

📌 Exemples d'utilisation

Comment je sauvegarde les options du jeu en clair, sans nœud ?

Un fichier JSON lisible est pratique pour des réglages que le joueur peut modifier à la main.

# Autoload « Options »
extends Node

var donnees := SaveData.new()

func _ready() -> void:
	donnees.system_id = "options"
	donnees.is_encrypted = false        # user://saves/options.json
	var relu := SaveManager.load(donnees, donnees.file_config)
	if relu:
		donnees.data = relu.data
	AudioServer.set_bus_volume_db(0, donnees.data.get("volume_db", 0.0))

func regler_volume(db: float) -> void:
	donnees.data["volume_db"] = db
	SaveManager.save(donnees, donnees.file_config)

Comment je sauvegarde une position (Vector2) ?

JSON ne connaît pas Vector2 : il serait relu sous forme de texte "(3.0, 4.0)" et ne serait pas réappliqué. Exposer des propriétés numériques qui décomposent le vecteur, et les suivre avec le binder :

var pos_x: float:
	get: return position.x
	set(v): position.x = v
var pos_y: float:
	get: return position.y
	set(v): position.y = v

# tracked_properties = ["pos_x", "pos_y"]

Comment je sauvegarde une ressource (statistiques, jauge) ?

resource_target vise une Resource quand node_target est vide. Ici une Gauge du module 🌡️ Stack And Flow : bornes d'abord, pour que la valeur ne soit pas rognée au rechargement.

func _ready() -> void:
	var lien := SaveDataBinder.new()
	add_child(lien)
	lien.save_data = SaveData.new()
	lien.save_data.system_id = "vie_joueur"
	lien.resource_target = $Joueur.vie        # une Gauge
	lien.tracked_properties = PackedStringArray(["min_value", "max_value", "current_value"])
	lien.load()

Comment je gère trois emplacements de sauvegarde ?

Changer le dossier de la SaveConfig de chaque SaveData avant de charger ou sauvegarder.

func choisir_emplacement(numero: int, systemes: Array[SaveData]) -> void:
	var config := SaveConfig.new()
	config.save_directory = "user://saves/emplacement_%d/" % numero
	for systeme in systemes:
		systeme.file_config = config

func emplacement_utilise(numero: int) -> bool:
	return DirAccess.dir_exists_absolute("user://saves/emplacement_%d/" % numero)

Comment je sais si l'écriture a échoué ?

SaveManager.save ne renvoie rien. Pour réagir (afficher un message, réessayer), passer par SaveFileAccess.write, qui renvoie un code d'erreur.

func sauvegarder(donnees: SaveData) -> bool:
	var erreur := SaveFileAccess.write(donnees, donnees.file_config)
	if erreur != OK:
		$Message.text = "Sauvegarde impossible : %s" % error_string(erreur)
	return erreur == OK

Comment je chiffre vraiment un fichier (clé dérivée d'un mot de passe) ?

Pour des données sensibles, le SecureChannel du module 🗄️ Multijoueur offre un chiffrement authentifié (AES-256 + HMAC, IV aléatoire). On l'utilise ici sur le JSON produit par SaveSerializer.

func ecrire_secret(donnees: SaveData, mot_de_passe: String) -> void:
	var sel := SecureChannel.random_bytes(16)
	var canal := SecureChannel.new()
	canal.set_key(SecureChannel.derive_key(mot_de_passe, sel))
	var paquet := canal.encrypt(SaveSerializer.serialize(donnees).to_utf8_buffer())
	var f := FileAccess.open("user://secret.bin", FileAccess.WRITE)
	f.store_buffer(sel + paquet)        # le sel n'est pas secret

func lire_secret(mot_de_passe: String) -> SaveData:
	var octets := FileAccess.get_file_as_bytes("user://secret.bin")
	var canal := SecureChannel.new()
	canal.set_key(SecureChannel.derive_key(mot_de_passe, octets.slice(0, 16)))
	var clair := canal.decrypt(octets.slice(16))
	return SaveSerializer.deserialize(clair.get_string_from_utf8()) if canal.get_last_error() == OK else null

🚧 Limitations

Format des données

  • Seuls les types JSON survivent. Vector2, Vector3, Color, Transform, objets… sont écrits sous forme de texte ("(3.0, 4.0)") et relus comme du texte. Le SaveDataBinder tente alors de réappliquer un texte sur une propriété vectorielle : Godot l'ignore sans erreur, la propriété garde sa valeur. Décomposer les vecteurs (voir exemple).
  • Les entiers reviennent en float (7 → 7.0). Réappliqués sur une propriété int, ils sont reconvertis ; lus directement dans data, penser à int().
  • Les clés de dictionnaire deviennent des textes (une clé 1 est relue "1").
  • Pas de versionnage : aucune migration si la structure des données change entre deux versions du jeu ; utiliser data.get("cle", valeur_par_defaut).

Chiffrement

  • Le début de la clé est écrit en clair. Le vecteur d'initialisation est formé des 16 premiers octets de la clé, et il est stocké en tête du fichier : ouvrir un .sav dans un éditeur hexadécimal révèle la moitié de la clé. Ce choix garde la compatibilité avec l'ancienne version C# du système.
  • Chiffrement déterministe et sans intégrité. Les mêmes données donnent toujours le même fichier, et aucune signature ne détecte une modification : un fichier altéré produit au mieux un JSON illisible.
  • La clé est dans le jeu. Quel que soit le chiffrement, la clé doit être présente dans l'exécutable ou ses ressources pour relire la sauvegarde : c'est une protection contre la curiosité, pas contre un tricheur.
  • Clé de 32 octets UTF-8. Plus courte, elle est complétée par des zéros ; plus longue, tronquée (les caractères accentués comptent pour 2 octets).

Fichiers et erreurs

  • Mauvaise clé = « aucune sauvegarde ». Une clé incorrecte, un fichier corrompu ou absent produisent tous null et le même message jaune (plus une erreur « Parse JSON failed » pour les deux premiers) : impossible de les distinguer par l'API.
  • Écriture non atomique. Le fichier est tronqué puis réécrit directement : un arrêt brutal pendant l'écriture laisse un fichier vide ou incomplet. Aucune copie de secours n'est conservée.
  • Synchrone. Lecture, écriture et chiffrement se font sur le fil principal ; sans conséquence pour quelques kilo-octets, perceptible pour de gros dictionnaires.
  • Changer is_encrypted change de fichier. L'extension en dépend : après le changement, l'ancien fichier n'est ni relu ni supprimé.
  • SaveManager.load ne modifie pas le SaveData passé : il renvoie un nouvel objet qui ne contient que system_id et data (chiffrement et SaveConfig par défaut). Recopier data soi-même (le binder le fait).
  • SaveManager.save ne renvoie pas d'erreur (voir exemple).

SaveDataBinder

  • Pas de sous-propriétés : "position:x" n'est pas lu. Passer par une propriété dédiée.
  • Une seule cible par binder (le nœud l'emporte sur la ressource) ; plusieurs binders peuvent partager un même SaveData, mais chacun réécrit tout le fichier à son save().
  • Rien n'est automatique : ni chargement à _ready, ni sauvegarde à la fermeture ; appeler load() et save() soi-même.

🏗️ Architecture

Composants et communication

  • SaveData (ressource) porte l'identifiant, le dictionnaire et les réglages de chiffrement ; elle possède une SaveConfig (ressource) créée à sa construction.
  • SaveManager, SaveFileAccess et SaveSerializer sont des classes statiques enregistrées comme abstraites (non instanciables) ; elles s'appellent en chaîne par appel direct : SaveManager → SaveFileAccess (chemin, dossier, chiffrement) → SaveSerializer (JSON). SaveManager ajoute la journalisation.
  • SaveDataBinder (nœud) lit et écrit les propriétés de sa cible par Object.get / Object.set, puis appelle SaveManager. Aucun signal n'est utilisé dans le module.

Dépendances et couplage

  • Dépendance de compilation vers l'en-tête custom_logger.hpp du 📰 Journal Console (fonction log_it en ligne) : aucune dépendance à l'exécution vers sa bibliothèque.
  • Aucun lien avec les autres modules ; le binder fonctionne avec n'importe quelle classe (y compris une Gauge, un script GDScript, une classe d'un autre module).
  • Bibliothèque propre : save_system_register.cpp → bin/save_system/.

Décisions de conception

ChoixPourquoi (ne pas « corriger » sans en tenir compte)
Un fichier par système de jeu (system_id)Sauvegarder les options ne réécrit pas la progression ; un fichier corrompu n'emporte qu'un système.
Format JSONLisible et éditable en clair pendant le développement, portable entre versions du moteur et avec l'ancienne version C#.
IV dérivé de la clé, bourrage par zérosReproduit exactement le format de l'ancienne version C# pour relire les sauvegardes existantes. Le remplacer (IV aléatoire, PKCS#7, HMAC) rendrait ces fichiers illisibles : prévoir une migration.
Bourrage retiré en supprimant les octets nuls finauxSûr car le JSON ne contient jamais d'octet nul.
Classes de service statiques et abstraitesAucun état à conserver entre deux appels : pas d'autoload à déclarer, pas d'instance à transmettre.
Cible du binder mémorisée par identifiant d'instance (ObjectID)Le nœud cible peut être libéré sans prévenir le binder : on ne garde pas de pointeur pendant.
pull_to_save_data écrit dans le dictionnaire existantLe Dictionary est partagé par référence : les clés ajoutées par d'autres codes dans le même SaveData sont conservées.
