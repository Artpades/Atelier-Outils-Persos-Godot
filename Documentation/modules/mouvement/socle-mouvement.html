🧩_MovementSystem - Mouvement & Physique - Documentation

Module Socle du mouvement : la base commune de tous les composants de déplacement (sol, nage, mur, vol, corde) et la page de référence de la catégorie.

Godot 4.7+ Bibliothèque bin/movement_physics 1 classe : MovementComponent 2D & 3D

📝 Présentation

Un personnage qui marche, nage, glisse le long d'un mur et grimpe à une corde finit souvent avec un unique script de 800 lignes plein de if en_l_eau … elif sur_un_mur …, que personne n'ose plus toucher. Ce module découpe le déplacement en composants indépendants qui parlent le même langage : chaque mode de déplacement est un nœud enfant du corps, et tous reçoivent la même intention (« aller par là », « sauter », « courir »).

🧩 MovementComponent — le contrat

Classe de base abstraite : l'intention (move, jump, set_running, set_vertical_input), la mémoire du saut, l'état actif / inactif, les gizmos de débogage et la méthode virtuelle _movement_step pour écrire ses propres modes en GDScript.

🗺️ La famille de composants

Sol, nage, mur, plané / vol, corde : chacun a sa page (liens plus bas). Un 🎬 Orchestrateur facultatif choisit lequel est actif selon la situation.

Pour qui ? Les développeurs gameplay qui assemblent un contrôleur de personnage (joueur ou IA) à partir de briques, et ceux qui veulent ajouter un mode de déplacement maison (échelle, véhicule, grappin) qui s'intègre au reste.

Ce que ce module n'est pas
  • Pas un nœud à ajouter tel quel : MovementComponent ne s'instancie pas, on ajoute un de ses descendants (🦶 Déplacement au sol, 🌊 Aquatique…).
  • Pas une gestion des entrées : il ne lit ni clavier ni manette. C'est votre script, une IA ou le module d'entrées qui appelle move() / jump().
  • Pas un choix automatique du mode : c'est le rôle de l'🎬 Orchestrateur de mouvement. Sans lui, tous les composants d'un corps sont actifs en même temps.

Mise en place

  1. Compiler la bibliothèque (si les binaires ne sont pas déjà présents) depuis la racine du dépôt : 
    scons movement_physics
    le fichier movement_physics_register.cpp fait de ce dossier une bibliothèque à part : seule elle est recompilée, et son .gdextension est régénéré.
  2. Copier le dossier bin/movement_physics/ dans le projet Godot, au même emplacement : res://bin/movement_physics/.
    le .gdextension référence ses binaires par des chemins res://bin/movement_physics/… ; ailleurs, Godot ne les trouve pas.
  3. Redémarrer l'éditeur après le premier ajout.
    Godot ne découvre les nouvelles extensions qu'au démarrage ; ensuite, les recompilations sont rechargées à chaud (reloadable = true).
  4. Vérifier : Ajouter un nœud filtré sur « Movement » doit proposer GroundMovement2D, MovementDirector… (MovementComponent apparaît grisé : classe abstraite). Le panneau Sortie affiche « 🌀Module Mouvement & Physique chargé avec succès ! ».
    si ce message manque, la bibliothèque n'est pas chargée : l'erreur est écrite juste au-dessus dans le panneau Sortie.

Aucun autoload ni réglage de projet n'est requis.

⚙️ Mode d'emploi

A. Faire marcher un personnage avec un composant

  1. Créer un CharacterBody2D avec une CollisionShape2D et un Sprite2D, et un sol (StaticBody2D).
    les composants déplacent leur parent : c'est lui qui doit être un corps physique.
  2. Ajouter un GroundMovement2D comme enfant direct du CharacterBody2D.
    un composant actif (c'est le cas par défaut) déplace le corps à chaque image physique : gravité et move_and_slide sont déjà gérés.
  3. Envoyer l'intention depuis un script attaché au corps : 
    extends CharacterBody2D

@onready var sol: GroundMovement2D = $GroundMovement2D

func _physics_process(_delta: float) -> void:
	sol.move(Vector2(Input.get_axis("ui_left", "ui_right"), 0))
	if Input.is_action_just_pressed("ui_accept"):
		sol.jump()
	elif Input.is_action_just_released("ui_accept"):
		sol.release_jump()   # relâcher tôt = saut plus court
    le composant ne lit pas les entrées : la même brique sert au joueur, à une IA ou à une cinématique.
  4. Activer debug_mode dans l'inspecteur du composant et lancer le jeu.
    flèche verte = vitesse, flèche jaune = intention, texte = état (« au sol · sauts 0/1 ») : on voit immédiatement si le composant reçoit bien les commandes.

B. Écrire son propre mode de déplacement (échelle)

  1. Créer un script qui hérite de MovementComponent et surcharger _movement_step : 
    class_name LadderMovement2D
extends MovementComponent

@export var vitesse := 120.0

func _movement_step(delta: float) -> void:
	var corps := get_body() as CharacterBody2D
	corps.velocity = Vector2(get_move_input().x * 40.0, get_move_input().y * vitesse)
	if has_jump_request(true):   # true : la demande est consommée
		corps.velocity.y = -300.0
		active = false           # quitter l'échelle
	corps.move_and_slide()
    _movement_step n'est appelée que si le composant est actif ; l'intention (get_move_input, demande de saut) est déjà stockée par la base.
  2. L'ajouter sous le corps, active décoché, et l'activer quand le joueur entre dans la zone de l'échelle (en désactivant le composant de sol, ou via un contexte de l'🎬 Orchestrateur).
    deux composants actifs en même temps appellent chacun move_and_slide : le corps bougerait deux fois par image.

💻 API Accessible

Référence générée depuis doc_classes/MovementComponent.xml. Seuls les éléments exposés à Godot figurent ici ; le reste est interne et peut changer sans préavis :

  • Les méthodes C++ protégées _physics_step, _on_activated, _on_deactivated, _draw_debug, _debug_text : points d'extension des classes C++ uniquement (en GDScript, utiliser _movement_step et les signaux activated / deactivated).
  • is_body_3d(), la mémoire du saut jump_buffer, et la classe C++ DebugGizmos (debug_gizmos.hpp) qui gère les gizmos de débogage de toute la catégorie, ainsi que la macro DEBUG_MODE_DECLARATIONS et les couleurs debug_colors.

📌 Exemples d'utilisation

Comment je fais déplacer une IA avec les mêmes composants que le joueur ?

L'IA n'a qu'à produire une intention. Ici, un ennemi qui patrouille et saute quand il bute contre un mur.

extends CharacterBody2D

var sens := 1.0

func _physics_process(_delta: float) -> void:
	var sol: GroundMovement2D = $GroundMovement2D
	if is_on_wall():
		if sol.is_on_floor() and randf() < 0.5:
			sol.jump()
		else:
			sens = -sens
	sol.move(Vector2(sens, 0))

Comment je rends le saut plus tolérant (appui juste avant l'atterrissage) ?

La demande de saut reste valable jump_buffer_time secondes : un appui 0,2 s avant de toucher le sol déclenche quand même le saut à l'atterrissage.

func _ready() -> void:
	$GroundMovement2D.jump_buffer_time = 0.2
	$GroundMovement2D.coyote_time = 0.15   # et 0,15 s de grâce après un rebord

Comment je fais subir le vent à mon composant GDScript ?

Les composants C++ ajoutent l'accélération des zones de force ; dans un composant maison, il faut le faire soi-même avec la méthode statique.

func _movement_step(delta: float) -> void:
	var corps := get_body() as CharacterBody2D
	corps.velocity += MovementComponent.external_acceleration_2d(corps) * delta
	corps.move_and_slide()

Comment je change d'animation quand un composant prend la main ?

func _ready() -> void:
	$SwimMovement2D.activated.connect(func(): $AnimationPlayer.play("nage"))
	$SwimMovement2D.deactivated.connect(func(): $AnimationPlayer.play("marche"))

Comment je relie les composants au module d'entrées ?

Avec un 🎬 MovementDirector, il suffit de parler au directeur : il relaie à tous les composants. Exemple avec les actions Godot standard :

func _physics_process(_delta: float) -> void:
	var d: MovementDirector = $MovementDirector
	d.move(Input.get_vector("ui_left", "ui_right", "ui_up", "ui_down"))
	d.set_running(Input.is_key_pressed(KEY_SHIFT))
	if Input.is_action_just_pressed("ui_accept"):
		d.jump()
	if Input.is_action_just_released("ui_accept"):
		d.release_jump()

🚧 Limitations

  • Sans orchestrateur, tous les composants sont actifs. Deux composants actifs sur un même corps le déplacent chacun (deux move_and_slide par image, gravité appliquée deux fois). Il faut soit un MovementDirector, soit gérer active soi-même.
  • Le composant doit être un enfant direct du corps. get_body() renvoie le parent, et l'orchestrateur, le recul et les zones de force ne cherchent que parmi les enfants directs.
  • L'intention est mémorisée. move(Vector2(1, 0)) fait avancer indéfiniment tant qu'on n'envoie pas Vector2.ZERO : penser à envoyer la commande à chaque image, ou à la remettre à zéro.
  • release_jump() n'efface pas la demande de saut : un appui très bref reste en mémoire jump_buffer_time secondes (c'est voulu, mais un saut peut donc partir après le relâchement).
  • Rien ne tourne dans l'éditeur : pas de prévisualisation du mouvement sans lancer le jeu.
  • debug_mode a un coût : plusieurs gizmos redessinés à chaque image physique par composant. À réserver au développement.
  • Pas de mise en réseau : l'état (intention, mémoire du saut) est local ; la synchronisation multijoueur reste à faire de votre côté.

🏗️ Architecture

Composants et communication

  • MovementComponent est un Node enregistré comme classe virtuelle (non instanciable). À NOTIFICATION_READY il active son traitement physique ; à chaque NOTIFICATION_PHYSICS_PROCESS, s'il est actif, il appelle l'étape C++ _physics_step puis la virtuelle GDScript _movement_step, décrémente la mémoire du saut et dessine ses gizmos.
  • Intention : de simples appels directs (move, jump…) qui stockent des valeurs ; aucun signal. Le MovementDirector les relaie par appel direct à chaque composant.
  • Environnement : les composants interrogent des fonctions statiques qui parcourent des registres d'instances — ForceZone2D::get_acceleration_on (via external_acceleration_2d), Knockback2D::active_on, WaterArea2D::find_containing, Rope2D::find_rope_of. Pas de singleton ni d'autoload.
  • Signaux : activated / deactivated à chaque changement d'active, plus les signaux propres à chaque composant (jumped, landed, wall_jumped…).

Dépendances et couplage

  • movement_component.cpp inclut force_zone.hpp (pour external_acceleration_*) : la base dépend des zones de force, d'où leur présence dans la même bibliothèque.
  • Les composants dépendent du socle (héritage) et, selon leur rôle, de Knockback, WaterArea ou Rope. Le socle, lui, ne connaît aucun composant concret.
  • Les gizmos réutilisent les fonctions inline de gizmos.hpp (module 🐛 Gizmos), compilées dans cette bibliothèque ; leurs ressources sont libérées au déchargement (GizmoResources::destroy()).
  • Toute la catégorie est compilée dans une seule bibliothèque (movement_physics_register.cpp → bin/movement_physics/). Un autre module ne doit pas inclure ses .hpp : il passe par Godot (ClassDB.instantiate("GroundMovement2D"), call("move", …)).

Décisions de conception

ChoixPourquoi (ne pas « corriger » sans en tenir compte)
Un composant par mode de déplacement, plutôt qu'un contrôleur uniqueChaque mode reste court et testable seul ; on compose un personnage dans l'arbre de scène, et un mode maison (GDScript) s'ajoute sans toucher au reste.
Intention commune (move / jump / set_running / set_vertical_input)Le joueur, une IA ou l'orchestrateur pilotent n'importe quel composant de la même façon ; changer de mode ne change pas le code d'entrée.
move borne la longueur à 1 au lieu de normaliserConserve les valeurs intermédiaires d'un stick analogique (marcher doucement) tout en empêchant la diagonale clavier d'aller plus vite.
Mémoire du saut dans la base (jump_buffer_time)Tous les composants bénéficient du même saut « tolérant », et l'orchestrateur n'a rien à gérer.
Actif par défautUn composant seul sous un corps fonctionne sans configuration ; l'orchestrateur ne gère que les composants qu'il cite.
Registres statiques d'instances (zones, eau, cordes, reculs) plutôt que des signaux body_enteredLe composant interroge l'état au moment où il en a besoin : pas de connexions à gérer ni d'état « entré / sorti » qui pourrait se désynchroniser.
Gizmos de débogage dessinés par le serveur de renduIls n'ajoutent aucun nœud à la scène et disparaissent complètement quand debug_mode est désactivé.
