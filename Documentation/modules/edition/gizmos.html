🐛_GizmoSystem - Édition et Debug - Documentation

Module Gizmos : dessiner des formes de debug 2D et 3D (lignes, flèches, boîtes, chemins, texte…) d'un simple appel, sans ajouter de nœud.

Godot 4.7+ Bibliothèque bin/tool_editor 2 classes : Gizmos2D · Gizmos3D 2D & 3D

📝 Présentation

Pour comprendre un bug de déplacement, d'IA ou de collision, il faut voir : la vitesse du personnage, le rayon de détection d'un ennemi, le chemin qu'il suit, la zone d'un déclencheur. Godot n'a pas de fonction « dessine une flèche ici » en 3D, et en 2D _draw() oblige à écrire le dessin dans le nœud lui-même. Ce module fournit ces dessins de debug prêts à l'emploi, depuis n'importe quel script, en 2D comme en 3D.

✏️ Gizmos2D

Lignes, flèches, cercles, rectangles, capsules, polygones, chemins (pointillés, Bézier, flèches), repère d'axes, icône et texte, dans le monde 2D.

🧊 Gizmos3D

Lignes et tubes, flèches, boîtes, sphères, cercles, rectangles, capsules, polygones, chemins, repère XYZ, frustum de caméra, icône et texte toujours face à la caméra.

Pour qui ? Les développeurs qui déboguent le gameplay, et les autres modules du toolkit : les gizmos de l'💻 Éditeur d'objet (GizmoHost), les poignées du ✋ Système de Handles et le mode debug des modules de 🌀 Mouvement & Physique s'en servent.

Ce que ce module n'est pas
  • Pas les gizmos de l'éditeur Godot (EditorNode3DGizmoPlugin) : ces dessins ne sont pas sélectionnables ni manipulables. Pour des poignées déplaçables, voir ✋ Système de Handles ; pour des gizmos configurés par type d'objet, l'💻 Éditeur d'objet.
  • Pas un outil de rendu de jeu : pas d'éclairage, pas d'ombre, pas de gestion de l'ordre d'affichage. C'est un outil de visualisation.

🛠️ Installation

Dépendances

DépendanceNaturePourquoi
Godot 4.7 ou plus récentObligatoirecompatibility_minimum = "4.7" dans le .gdextension.
Bibliothèque bin/tool_editor/Obligatoire pour GDScriptElle enregistre Gizmos2D et Gizmos3D (avec tous les outils d'édition et de debug).
Icône res://🖼️Editor Icons/🧰🧑‍💻/Pix. Gizmos Icon.pngOptionnelleIcône des deux classes dans l'éditeur.

Côté C++, un autre module peut dessiner sans la bibliothèque : toutes les fonctions sont définies dans gizmos.hpp (classe Gizmos). Il doit alors appeler GizmoResources::destroy() au déchargement de son propre module (comme movement_physics_register.cpp).

Mise en place

  1. Compiler la bibliothèque si nécessaire : 
    scons tool_editor
    compile la bibliothèque des outils d'édition et régénère son .gdextension.
  2. Copier bin/tool_editor/ dans res://bin/tool_editor/, puis redémarrer l'éditeur.
    chemins res://bin/tool_editor/… dans le .gdextension ; extension découverte au démarrage.

Aucun nœud, autoload ni réglage : les deux classes sont statiques.

⚙️ Mode d'emploi

Afficher en 3D la vitesse d'un CharacterBody3D :

  1. Créer le gizmo une fois, dans _ready : 
    extends CharacterBody3D

var gizmo_vitesse: RID

func _ready() -> void:
	gizmo_vitesse = Gizmos3D.create_3D_gizmo(get_viewport())
    un gizmo est un objet du serveur de rendu, rattaché au monde 3D du viewport. On le garde dans une variable (RID) pour le redessiner et le libérer.
  2. Le redessiner chaque frame : 
    func _physics_process(_delta: float) -> void:
	move_and_slide()
	var bout := global_position + velocity * 0.3
	Gizmos3D.draw_3D_arrow(gizmo_vitesse, global_position, bout, Color.CYAN, 0.2, 2.0)
    chaque appel remplace la forme précédente : la flèche suit le personnage. Les coordonnées sont globales.
  3. Le libérer quand le nœud quitte l'arbre : 
    func _exit_tree() -> void:
	Gizmos3D.free_3D_gizmo(gizmo_vitesse)
    le gizmo n'appartient à aucun nœud : sans cette ligne, la flèche resterait affichée après la disparition du personnage.

En 2D, c'est identique avec Gizmos2D.create_2D_gizmo, draw_2D_* et free_2D_gizmo.

💻 API Accessible

Référence générée depuis doc_classes/Gizmos2D.xml et doc_classes/Gizmos3D.xml. Éléments internes, non exposés :

  • La classe C++ Gizmos (gizmos.hpp), qui contient l'implémentation ; Gizmos2D et Gizmos3D ne font que lier ses fonctions. Ses aides privées (_add_3D_thick_line, _add_3D_arrow_to_surfacetool, _add_3D_point_marker, _draw_2D_polyline_circle, _add_2D_arrow, _get_or_create_mesh_rid, _get_scenario).
  • GizmoResources : registres des maillages et matériaux par gizmo 3D, shader du texte, matériau par défaut, libérés au déchargement de la bibliothèque.

📌 Exemples d'utilisation

Comment j'affiche plusieurs formes en même temps ?

Un gizmo ne garde qu'une forme : créer un gizmo par forme, dans un dictionnaire.

extends Node3D

var gizmos := {}

func _ready() -> void:
	for nom in ["portee", "cible", "nom"]:
		gizmos[nom] = Gizmos3D.create_3D_gizmo(get_viewport())

func _process(_delta: float) -> void:
	Gizmos3D.draw_3D_sphere(gizmos.portee, global_position, 5.0, Color(1, 0.5, 0))
	Gizmos3D.draw_3D_line(gizmos.cible, global_position, $"../Joueur".global_position, Color.RED)
	Gizmos3D.draw_3D_text(gizmos.nom, global_position + Vector3.UP * 2.2, "Garde", Color.WHITE)

func _exit_tree() -> void:
	for rid in gizmos.values():
		Gizmos3D.free_3D_gizmo(rid)

Comment je visualise le chemin d'une IA ?

Avec as_arrows pour le sens, show_points pour les étapes. En 3D, réduire arrow_head_size (en mètres).

func montrer_chemin(points: PackedVector3Array) -> void:
	Gizmos3D.draw_3D_path(gizmo_chemin, points,
		true,   # as_arrows
		1,      # segments_per_line
		0.1,    # spacing : petit écart entre les flèches
		false,  # use_bezier
		true,   # show_points
		0.08,   # point_radius
		2.0,    # width
		Color.GREEN_YELLOW,
		0.25)   # arrow_head_size

Comment je montre la portée d'une tourelle 2D en pointillés ?

extends Node2D

@export var portee := 150.0
var g_portee: RID
var g_visee: RID

func _ready() -> void:
	g_portee = Gizmos2D.create_2D_gizmo(get_viewport())
	g_visee = Gizmos2D.create_2D_gizmo(get_viewport())

func _process(_delta: float) -> void:
	Gizmos2D.draw_2D_circle(g_portee, global_position, portee, Color(1, 0, 0, 0.6))
	var cercle := PackedVector2Array()
	for i in 41:
		cercle.append(global_position + Vector2.RIGHT.rotated(TAU * i / 40.0) * portee * 0.5)
	Gizmos2D.draw_2D_path(g_visee, cercle, false, 1, 4.0)  # spacing 4 px : pointillés

func _exit_tree() -> void:
	Gizmos2D.free_2D_gizmo(g_portee)
	Gizmos2D.free_2D_gizmo(g_visee)

Comment je dessine le champ de vision d'une caméra de surveillance ?

func _process(_delta: float) -> void:
	var cam: Camera3D = $Camera3D
	var aspect := 16.0 / 9.0
	Gizmos3D.draw_3D_camera_frustum(g_frustum, cam.global_transform, cam.fov, cam.near, 8.0, aspect, Color.MAGENTA)

Comment je vérifie l'orientation d'un objet ?

Gizmos3D.draw_3D_origin(g_repere, $Arme.global_transform, 0.5, 0.1)   # X rouge, Y vert, Z bleu
Gizmos2D.draw_2D_origin(g_repere_2d, $Vaisseau.global_transform, 40.0)  # X rouge, Y vert

Comment je masque tous mes dessins de debug d'une touche ?

clear_* efface sans libérer : il suffit de ne plus redessiner.

var debug_visible := true

func _unhandled_input(event: InputEvent) -> void:
	if event.is_action_pressed("debug_toggle"):
		debug_visible = not debug_visible
		if not debug_visible:
			Gizmos3D.clear_3D_gizmo(gizmo_vitesse)

func _physics_process(_delta: float) -> void:
	if debug_visible:
		Gizmos3D.draw_3D_arrow(gizmo_vitesse, global_position, global_position + velocity * 0.3, Color.CYAN, 0.2, 2.0)

Comment je donne un matériau personnalisé à un gizmo 3D ?

Le shader doit lire COLOR pour garder la couleur passée aux méthodes. Exemple : un tracé visible à travers les murs.

var mat := ShaderMaterial.new()
mat.shader = Shader.new()
mat.shader.code = """
shader_type spatial;
render_mode unshaded, depth_test_disabled, cull_disabled;
void fragment() { ALBEDO = COLOR.rgb; ALPHA = COLOR.a; }
"""
Gizmos3D.apply_shader_on_gizmo(gizmo_chemin, mat)

🚧 Limitations

Communes

  • Un gizmo = une forme. Chaque draw_* efface le dessin précédent du gizmo. Il faut un gizmo par forme affichée simultanément.
  • Libération manuelle obligatoire. Un gizmo n'est lié à aucun nœud : sans free_*_gizmo, il reste affiché et occupe de la mémoire jusqu'à la fermeture du jeu, même après un changement de scène.
  • Certains appels ignorés laissent l'ancien dessin au lieu d'effacer : chemin de moins de 2 points, polygone 2D de moins de 2 points, polygone 3D de moins de 3 points, flèche 3D de longueur nulle.
  • Erreurs en console seulement. Un RID invalide écrit un message rouge et l'appel est ignoré ; rien n'est renvoyé.
  • Coût : en 3D, chaque appel reconstruit un maillage complet (tubes, sphères, texte glyphe par glyphe) côté CPU. Des dizaines de gizmos redessinés chaque frame restent raisonnables ; des centaines pèsent sur les performances. Ne redessiner que ce qui bouge.
  • Visibles en jeu exporté : rien ne désactive les gizmos en release ; conditionner soi-même avec OS.is_debug_build().

Gizmos2D

  • apply_shader_on_gizmo ne fonctionne pas. Le matériau transmis au serveur de rendu est toujours vide (la méthode lit un identifiant de shader que les matériaux natifs ne fournissent pas) : l'appel retire le matériau au lieu de l'appliquer. Avec null, le moteur plante (vérifié en headless).
  • draw_2D_capsule et draw_2D_origin déplacent le gizmo (transformation appliquée au gizmo, jamais réinitialisée) : réutiliser ce gizmo pour une ligne ou un cercle les décale d'autant.
  • Coordonnées du monde 2D : le dessin suit la Camera2D. Pour un dessin fixe à l'écran (HUD), il faut convertir soi-même les positions. Aucun z_index n'est réglé : l'ordre par rapport aux sprites n'est pas maîtrisé.
  • Capsule uniquement verticale et en contour ; antialiasing sans effet sur les lignes de draw_2D_path et sur les formes pleines.
  • Texte : police de repli du thème uniquement, une seule ligne, position = ligne de base.

Gizmos3D

  • Icône et texte modifient le gizmo durablement : draw_3D_icon et draw_3D_text déplacent le gizmo et changent (ou retirent) son matériau. Dessiner ensuite une autre forme sur ce gizmo la décale et lui donne un mauvais matériau. Réserver un gizmo à l'icône ou au texte.
  • arrow_head_size de draw_3D_path vaut 12 par défaut, soit 12 m : chaque tronçon devient un cône. Toujours le préciser (≈ 0,2).
  • Épaisseurs liées aux unités du monde : width > 1 donne un tube de rayon width × 0,005 m, qui paraît fin de loin et épais de près ; width ≤ 1 donne une ligne d'un pixel. Flèches et repères sont toujours des tubes.
  • Boîtes alignées sur les axes (draw_3D_cube sans rotation), capsules verticales uniquement, orientation des rectangles autour de leur normale non choisie.
  • Masqués par la géométrie (test de profondeur actif), sauf les icônes ; pour voir à travers les murs, appliquer un matériau depth_test_disabled (voir exemple).
  • Polygone plein correct seulement s'il est plan et convexe (triangulation en éventail).
  • Texte : une ligne, gauche à droite, police de repli du thème ; le filtrage d'une icône est figé au premier appel.
  • Un gizmo 3D appartient à la bibliothèque qui l'a créé : en C++, le créer et le libérer depuis le même module (chaque bibliothèque a ses propres registres). Sans conséquence en GDScript.

🏗️ Architecture

Composants et communication

  • Gizmos (C++ pur, non enregistré) contient toutes les fonctions, en inline dans le header. Gizmos2D et Gizmos3D (RefCounted sans état) lient directement ces fonctions comme méthodes statiques.
  • 2D : un gizmo est un canvas_item du RenderingServer, enfant du canvas du World2D du viewport. Chaque dessin fait canvas_item_clear puis ajoute ses primitives.
  • 3D : un gizmo est une instance du RenderingServer dans le scenario du World3D, avec le matériau par défaut en material_override. Chaque dessin vide le maillage associé (créé au premier dessin) et y ajoute une surface construite avec SurfaceTool.
  • Texte 3D : mis en forme par le TextServer ; chaque glyphe devient un quad qui pointe dans l'atlas de la police, avec un matériau par page d'atlas et un shader commun qui oriente le texte vers la caméra.
  • GizmoResources détient les registres (maillage et matériaux par gizmo, shader du texte, matériau par défaut), créés au premier usage et libérés par GizmoResources::destroy() au déchargement du module.

Dépendances et couplage

  • Ne dépend d'aucun autre module.
  • Inclus (header) par ✋ Système de Handles, 💻 Éditeur d'objet (GizmoHost) et les modules de 🌀 Mouvement & Physique (DebugGizmos, Knockback, ForceZone, Jiggle…). Chaque bibliothèque qui l'inclut possède son propre exemplaire de GizmoResources.

Décisions de conception

ChoixPourquoi (ne pas « corriger » sans en tenir compte)
Dessin direct par le RenderingServer, sans nœudAucun nœud parasite dans l'arbre (ni dans les scènes enregistrées) ; dessinable depuis n'importe quel objet, y compris une ressource ou un plugin.
Implémentation inline dans le headerLes autres bibliothèques du toolkit (mouvement, physique) dessinent leurs gizmos sans dépendre de tool_editor.
GizmoResources détruit explicitement au déchargementDes variables statiques étaient détruites après le moteur : RID perdus et risque de plantage. Classe C++ ordinaire (pas une classe Godot) pour que plusieurs bibliothèques puissent l'inclure sans conflit d'enregistrement.
Tube hexagonal quand width > 1Les lignes du GPU font toujours un pixel : seul un vrai volume donne une épaisseur.
Primitive (lignes / triangles) choisie selon la même règle que les tubesMélanger lignes à 2 sommets et triangles dans un même tampon donne l'erreur « Vertex amount must be a multiple of 3 ».
Texte 3D par TextServer plutôt que Label3D ou viewport hors écranAucun nœud ni texture intermédiaire ; le shaping (crénage, polices de repli) reste celui du moteur.
Grille 3D non portéeExclue volontairement lors du portage depuis gizmos_manager.gd.
