⚙️_ManagerBuilder - Édition et Debug - Documentation

Module Générateur de Gestionnaire : un gestionnaire unique par type, créé à la demande et conservé d'une scène à l'autre, sans autoload.

Godot 4.7+ Bibliothèque bin/tool_editor 1 classe : ManagerBuilder GDScript & C++

📝 Présentation

Un gestionnaire de caméras, de scènes ou d'inventaire doit exister une seule fois. Avec un autoload, il faut le déclarer dans chaque projet ; en le plaçant dans les scènes, on se retrouve avec un doublon à chaque scène chargée. Ce module garantit l'unicité : le gestionnaire est créé la première fois qu'on le demande, ou adopté s'il est déjà dans la scène, et toute copie supplémentaire est détruite.

🏭 Créer à la demande

make_getter("CameraManager") renvoie le gestionnaire existant ou le crée sous la racine de l'arbre, où il survit aux changements de scène.

🛡️ Éliminer les doublons

init_instance(nom, self), appelé par le gestionnaire à son entrée dans l'arbre, garde le premier et détruit les suivants.

Pour qui ? Les développeurs qui écrivent des gestionnaires : en C++ dans les autres modules du toolkit (CameraManager, SceneManager l'utilisent déjà), ou en GDScript.

Ce que ce module n'est pas
  • Pas un conteneur d'injection de dépendances : un nom = un nœud, sans interface, sans portée ni durée de vie configurables.
  • Pas un chargeur de scènes ou de scripts : seules les classes natives (moteur ou GDExtension) peuvent être créées ; un gestionnaire GDScript doit s'enregistrer lui-même.

⚙️ Mode d'emploi

Écrire un gestionnaire GDScript unique, présent dans plusieurs scènes :

  1. S'enregistrer à l'entrée dans l'arbre et s'arrêter si l'on est un doublon : 
    extends Node  # script « inventaire.gd », nœud placé dans chaque niveau

var objets: Array[String] = []

func _enter_tree() -> void:
	if ManagerBuilder.init_instance(&"Inventaire", self) != self:
		return  # une instance existe déjà : celle-ci va être détruite
    le premier inventaire devient l'instance de référence ; les suivants sont détruits par queue_free et ne doivent rien initialiser.
  2. Se désenregistrer en sortant de l'arbre : 
    func _exit_tree() -> void:
	ManagerBuilder.unregister_instance(&"Inventaire", self)
    sans cela, un nœud sorti de l'arbre mais pas encore libéré resterait renvoyé par make_getter. Un doublon qui se désenregistre n'efface pas l'instance de référence.
  3. Le récupérer depuis n'importe quel script : 
    var inventaire = ManagerBuilder.make_getter(&"Inventaire")
if inventaire:
	inventaire.objets.append("Clé")
    make_getter consulte d'abord le registre : il retrouve le gestionnaire GDScript enregistré. S'il n'y en a pas, il renvoie null (une classe GDScript ne peut pas être créée par le module).
  4. Persister d'une scène à l'autre (facultatif) : déplacer le nœud sous la racine à la première initialisation. 
    func _ready() -> void:
	if is_queued_for_deletion():
		return  # doublon (son _ready est quand même appelé)
	if get_parent() != get_tree().root:
		reparent.call_deferred(get_tree().root)
    un nœud placé dans une scène est détruit avec elle ; sous la racine, il survit à change_scene_to_file. Les nœuds créés par make_getter y sont placés d'office.

💻 API Accessible

Référence générée depuis doc_classes/ManagerBuilder.xml. Éléments internes, non exposés :

  • Le registre _get_registry() (table statique StringName → ObjectID) et _resolve(), qui purge les entrées dont l'objet a été libéré.
  • Les fonctions C++ manager_builder::get / init / release / is_available de manager_builder_access.hpp, destinées aux autres modules C++ (voir exemple).

📌 Exemples d'utilisation

Comment je récupère un gestionnaire du toolkit sans l'avoir mis dans la scène ?

Les gestionnaires natifs sont créés à la demande. Attention : le nœud est ajouté à l'arbre en différé, son _ready n'a pas encore été appelé au retour.

func _ready() -> void:
	var cameras = ManagerBuilder.make_getter(&"CameraManager")
	await get_tree().process_frame   # laisser le temps au nœud d'entrer dans l'arbre
	print(cameras.name)              # « CameraManager (Singleton) »

Comment je partage un nœud du moteur entre toutes les scènes ?

N'importe quelle classe native dérivée de Node convient, par exemple un lecteur de musique d'ambiance unique :

func jouer_ambiance(flux: AudioStream) -> void:
	var lecteur: AudioStreamPlayer = ManagerBuilder.make_getter(&"AudioStreamPlayer")
	lecteur.stream = flux
	lecteur.play.call_deferred()  # le nœud n'est dans l'arbre qu'à la fin de la frame

La clé du registre est le nom de classe : un seul AudioStreamPlayer peut être géré ainsi. Pour plusieurs, enregistrer ses propres nœuds sous des clés différentes avec init_instance.

Comment je recrée un gestionnaire (nouvelle partie) ?

func nouvelle_partie() -> void:
	var ancien = ManagerBuilder.make_getter(&"Inventaire")
	if ancien:
		ManagerBuilder.unregister_instance(&"Inventaire", ancien)
		ancien.queue_free()
	# le prochain inventaire qui entre dans l'arbre deviendra l'instance de référence

Comment j'en fais profiter un gestionnaire C++ d'un autre module ?

Un autre module GDExtension ne peut pas appeler directement le code de tool_editor : il inclut manager_builder_access.hpp, qui passe par ClassDB (modèle de CameraManager et SceneManager).

#include "1.🧰Ensemble d'Outils/0.🧑‍💻Édition et Debug🪳/⚙️Générateur de Gestionnaire/manager_builder_access.hpp"

static ObjectID instance_id;
MonManager *MonManager::get_instance() { return manager_builder::get<MonManager>(instance_id); }
void MonManager::_enter_tree() { if (!manager_builder::init(instance_id, this)) return; /* ... */ }
void MonManager::_exit_tree() { manager_builder::release(instance_id, this); }

🚧 Limitations

  • Plantage avec une classe RefCounted. make_getter(&"Resource") (ou toute classe dérivée de RefCounted) fait planter le moteur (vérifié en headless) : l'objet créé est libéré par le moteur avant d'être détruit une seconde fois par le module. Ne passer que des noms de classes dérivées de Node. Une classe Object simple est, elle, correctement refusée.
  • Création réservée aux classes natives. Un class_name GDScript n'est pas dans ClassDB : make_getter ne peut que le retrouver une fois enregistré par init_instance (vérifié).
  • Ajout à l'arbre différé. Le nœud renvoyé par une création n'est pas encore dans l'arbre : pas de _ready, pas de get_tree() avant la fin de la frame (vérifié).
  • Le doublon n'est détruit qu'en fin de frame (queue_free) et son _enter_tree continue : c'est au script de s'arrêter (return) quand init_instance ne le renvoie pas.
  • Un nom = une instance, pour tout le projet. Le registre est global et n'est jamais vidé par un changement de scène ; deux systèmes qui utilisent la même clé se partagent le même nœud.
  • Un gestionnaire placé dans une scène n'est pas déplacé sous la racine : il est détruit avec sa scène (le registre l'oublie alors automatiquement), à moins de le reparenter soi-même.
  • Pas de garde-fou de type. init_instance(&"CameraManager", un_label) est accepté : la clé n'est pas comparée à la classe du nœud.
  • Non sûr entre threads : le registre est une table statique sans verrou ; n'appeler les méthodes que depuis le thread principal.
  • Erreurs signalées en console seulement (texte rouge), avec un retour null : tester le résultat.

🏗️ Architecture

Composants et communication

  • ManagerBuilder n'a que des méthodes statiques, appelées directement. Son registre est une HashMap<StringName, ObjectID> statique propre à la bibliothèque tool_editor, donc unique dans le projet.
  • Chaque lecture résout l'ObjectID par instance_from_id : un nœud libéré donne null, et l'entrée est alors retirée.
  • make_getter crée via ClassDBSingleton::instantiate, nomme le nœud "X (Singleton)", l'enregistre avant de l'ajouter (call_deferred("add_child") sur la racine). Quand le nœud entre dans l'arbre et appelle init_instance, il se trouve déjà enregistré et reste l'instance de référence.
  • Les autres modules C++ passent par manager_builder_access.hpp (class_call_static), avec un cache ObjectID local qui prend le relais si tool_editor est absente.

Dépendances et couplage

  • Ne dépend d'aucune autre classe du toolkit.
  • Utilisé par 🎞️ Gestion de Caméras (CameraManager), 🎬 Gestionnaire de scènes (SceneManager) et, dans la même bibliothèque, par ✋ Système de Handles. Le couplage va de ces modules vers ManagerBuilder, et seulement via ClassDB pour les modules extérieurs.

Décisions de conception

ChoixPourquoi (ne pas « corriger » sans en tenir compte)
Registre plutôt que recherche par nom dans l'arbre (find_child)La version GDScript d'origine cherchait « X » alors que le nœud s'appelait « X (Singleton) » : elle ne retrouvait jamais l'instance. Le registre est la seule source de vérité.
ObjectID plutôt que pointeurUn gestionnaire libéré sans désenregistrement laisserait un pointeur invalide ; l'ObjectID se résout en null sans risque.
Classes natives uniquement pour la créationLe module gère les singletons natifs du framework, pas des scripts chargés dynamiquement (pas de Script ni de PackedScene).
Ajout différé à la racineÉvite de modifier l'arbre pendant une transition de scène ou un parcours en cours (erreur « parent busy »).
Accès par ClassDB depuis les autres modulesChaque module est une bibliothèque séparée : inclure manager_builder.hpp ailleurs ne serait pas lié. Passer par ClassDB évite aussi une dépendance dure à tool_editor.
