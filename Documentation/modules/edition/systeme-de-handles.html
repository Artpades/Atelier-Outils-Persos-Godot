✋_HandleSystem - Édition et Debug - Documentation

Module Système de Handles : des poignées 2D et 3D que l'on survole et fait glisser à la souris, pour éditer des valeurs directement dans la vue.

Godot 4.7+ Bibliothèque bin/tool_editor 1 classe : HandlersManager ⚠️ Non enregistré
⚠️ Module inactif dans la version actuelle

Le code de HandlersManager est compilé dans bin/tool_editor/, mais la classe n'est enregistrée nulle part : aucun GDREGISTER_CLASS(HandlersManager) dans tool_editor_register.cpp (la ligne de l'ancien register.cpp est commentée). Depuis Godot, ClassDB.class_exists("HandlersManager") renvoie false (vérifié en headless) : aucune méthode ni aucun signal ci-dessous n'est utilisable tant que l'enregistrement n'est pas ajouté. Cette page décrit le comportement du code tel qu'il est écrit.

📝 Présentation

Régler une position, un rayon ou un point de passage se fait d'ordinaire en tapant des nombres dans l'inspecteur. Il est bien plus naturel de saisir une poignée et de la faire glisser dans la vue. Ce module détecte, pour des zones rectangulaires (2D) ou des boîtes (3D), le survol de la souris et le glissement au bouton gauche, les dessine, et annonce chaque déplacement par un signal : votre code décide quoi modifier.

Pour qui ? Les développeurs d'outils d'édition (fenêtres d'édition, plugins, éditeurs en jeu) qui veulent des manipulateurs visuels, dans le viewport du jeu, un viewport de l'éditeur ou une 🪟 Fenêtre d'édition.

Ce que ce module n'est pas
  • Pas un système de sélection ou de glisser-déposer de jeu : pour déplacer des objets du jeu par le joueur, voir ✊ Glisser-Déposer d'objet.
  • Pas les poignées natives de l'éditeur (EditorNode3DGizmo) : ces poignées ne sont pas intégrées à l'annulation de l'éditeur ni à la sélection.
  • Pas un dessinateur : le dessin des poignées est délégué à 🐛 Gizmos.

Mise en place

  1. Activer la classe (modification de code, à faire par le mainteneur) : dans tool_editor_register.cpp, inclure "✋Système de Handles/handlers_manager.hpp" et ajouter GDREGISTER_CLASS(HandlersManager); au niveau SCENE, après ManagerBuilder.
    c'est l'étape qui manque aujourd'hui : l'enregistrement rend la classe, ses méthodes et ses signaux visibles de Godot et permet à ManagerBuilder de l'instancier.
  2. Compiler : 
    scons tool_editor
    reconstruit la bibliothèque ; le Sconstruct génère alors doc_classes/HandlersManager.xml à jour (méthodes et signaux), ce qui remplira la section API de cette page.
  3. Copier bin/tool_editor/ dans res://bin/tool_editor/ et redémarrer l'éditeur.
    chemins res://bin/tool_editor/… dans le .gdextension ; extension découverte au démarrage.

Aucun autoload : le gestionnaire est créé à la demande sous la racine de l'arbre par HandlersManager.get_singleton().

⚙️ Mode d'emploi

Une fois la classe enregistrée, déplacer un Sprite2D en tirant une poignée :

  1. Récupérer le gestionnaire et écouter son signal de déplacement : 
    extends Sprite2D

var handles

func _ready() -> void:
	handles = HandlersManager.get_singleton()
	handles.handle_2d_moved.connect(_on_handle_moved)
    un seul gestionnaire existe pour tout le projet ; il est créé au premier appel et ajouté à l'arbre à la fin de la frame.
  2. Enregistrer une poignée sous un identifiant unique : 
    	var zone := Rect2(position - Vector2(8, 8), Vector2(16, 16))
	handles.register_handle_2d(&"sprite_pos", zone, get_viewport())
    le rectangle est la zone sensible, en coordonnées du viewport ; le viewport indique où dessiner la poignée et où lire la souris.
  3. Appliquer le déplacement reçu : 
    func _on_handle_moved(id: StringName, coin: Vector2) -> void:
	if id == &"sprite_pos":
		position = coin + Vector2(8, 8)  # le signal donne le coin supérieur gauche
    le gestionnaire ne modifie aucun objet lui-même : c'est l'écouteur qui décide de ce que représente la poignée.
  4. Retirer la poignée en quittant l'arbre : 
    func _exit_tree() -> void:
	handles.unregister_handle_2d(&"sprite_pos")
    libère le gizmo de la poignée ; sinon elle reste affichée et testée.

Le fichier doc_classes/HandlersManager.xml ne contient que la description de la classe : tant qu'elle n'est pas enregistrée, Godot ne peut pas générer la liste de ses membres. Éléments internes : les structures Handle2D / Handle3D, les tables _handles_2d / _handles_3d, _process_2d_handles, _process_3d_handles, _redraw_handle_* et _is_viewport_effectively_visible.

📌 Exemples d'utilisation

Ces exemples supposent la classe enregistrée (voir Mise en place).

Comment je déplace un point de passage 3D à la souris ?

extends Marker3D

const ID := &"waypoint_1"
var handles

func _ready() -> void:
	handles = HandlersManager.get_singleton()
	var boite := AABB(global_position - Vector3.ONE * 0.25, Vector3.ONE * 0.5)
	handles.register_handle_3d(ID, boite, get_viewport())
	handles.handle_3d_moved.connect(func(id, centre):
		if id == ID:
			global_position = centre)

func _exit_tree() -> void:
	handles.unregister_handle_3d(ID)

Le glissement se fait dans le plan perpendiculaire à la direction de la caméra au moment du clic : pour changer la profondeur, tourner la caméra.

Comment je pose des poignées dans une fenêtre d'édition ?

Combinaison avec 🪟 Fenêtre d'édition : le viewport à fournir est la Window elle-même. Tant qu'elle est masquée, ses poignées ne sont ni testées ni redessinées.

var fenetre := WindowEditor.new()

func _ready() -> void:
	fenetre.open_window()
	var fond := ColorRect.new()
	fond.set_anchors_and_offsets_preset(Control.PRESET_FULL_RECT)
	fond.mouse_filter = Control.MOUSE_FILTER_IGNORE
	fenetre.add_control_to_window(fond)
	HandlersManager.get_singleton().register_handle_2d(&"curseur", Rect2(100, 100, 20, 20), fond.get_window())

Comment je fais suivre une poignée à un objet animé ?

func _process(_delta: float) -> void:
	if not handles.is_handle_2d_dragging(&"cible"):
		handles.set_handle_2d_rect(&"cible", Rect2($Cible.position - Vector2(8, 8), Vector2(16, 16)))

🚧 Limitations

  • Inutilisable en l'état : classe non enregistrée (vérifié en headless). Tout ce qui suit est tiré de la lecture du code, non testé en conditions réelles.
  • Coordonnées 2D incohérentes avec une caméra. La souris est lue en coordonnées du viewport (get_mouse_position) mais la poignée est dessinée dans le canvas du monde 2D, qui suit la Camera2D. Avec une caméra déplacée ou zoomée, le dessin et la zone sensible ne coïncident plus.
  • Pas de détection de clic, seulement de bouton enfoncé. Appuyer à côté puis glisser sur une poignée la saisit ; plusieurs poignées superposées sont saisies ensemble. Le clic n'est pas consommé : il atteint aussi le jeu ou l'éditeur en dessous.
  • Signal de déplacement à chaque frame pendant le glissement, même si la souris ne bouge pas.
  • Pas de lien avec l'annulation (Ctrl+Z) de l'éditeur : c'est à l'écouteur d'enregistrer ses actions.
  • Boîte 3D toujours alignée sur les axes et glissement limité au plan face à la caméra ; pas de contrainte d'axe. Sans caméra (ni explicite, ni active), la poignée 3D est ignorée.
  • Un identifiant ré-enregistré remplace la poignée sans libérer l'ancien dessin : le gizmo précédent reste affiché. Appeler unregister_* avant.
  • Visibilité d'un SubViewport : déduite du premier Control parent ; sans Control au-dessus, le viewport est toujours considéré comme visible.
  • Doublon mal détruit : un second HandlersManager placé dans une scène est mis en file de destruction par ManagerBuilder mais active quand même son traitement pour la frame en cours.

🏗️ Architecture

Composants et communication

  • HandlersManager (Node) s'enregistre auprès de ManagerBuilder à son entrée dans l'arbre et parcourt ses poignées à chaque _process.
  • Chaque poignée mémorise son viewport (et sa caméra) par ObjectID : si le viewport est détruit ou masqué, la poignée est simplement ignorée.
  • Le gizmo de dessin est créé paresseusement au premier traitement (le viewport n'est pas forcément dans l'arbre au moment de l'enregistrement), redessiné au changement de survol et pendant le glissement.
  • La communication vers l'extérieur se fait uniquement par signaux : le gestionnaire ne connaît pas l'objet édité.
  • À la sortie de l'arbre, tous les gizmos sont libérés et le gestionnaire se désenregistre.

Dépendances et couplage

  • Dépend de ⚙️ Générateur de Gestionnaire et de 🐛 Gizmos, appelés directement en C++ (même bibliothèque).
  • Aucun module ne dépend de lui aujourd'hui.

Décisions de conception

ChoixPourquoi (ne pas « corriger » sans en tenir compte)
Viewport fourni explicitement à l'enregistrementUne poignée peut vivre dans le jeu, dans un viewport de l'éditeur ou dans une fenêtre d'édition : le gestionnaire ne devine pas son origine.
Signaux plutôt que Callable ou propriété modifiée directementPas de couplage : n'importe quel objet décide de ce que la poignée représente.
Plan de glissement 3D figé au clicRecalculer le plan à chaque frame ferait dériver la poignée en profondeur.
Viewport masqué = poignée ignoréeUne fenêtre d'édition fermée ne doit pas capter les clics du jeu.
Viewport sans Control parent considéré visibleMieux vaut une poignée active de trop qu'un cas d'usage bloqué sans explication.
