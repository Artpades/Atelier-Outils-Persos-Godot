💻️_ObjectEditorSystem - Édition et Debug - Documentation

Module Éditeur d'objet : des interfaces d'édition générées automatiquement pour n'importe quel objet, en jeu comme dans l'éditeur.

Godot 4.7+ Bibliothèque bin/tool_editor 64 classes exposées Jeu & éditeur

📝 Présentation

Régler la vitesse du joueur pendant une partie, inspecter l'ennemi qui bugue, construire un menu d'options, donner aux game designers un panneau propre pour chaque type d'objet : à chaque fois, il faut écrire à la main des dizaines de champs, les relier aux propriétés, gérer l'annulation et les rafraîchir quand la valeur change ailleurs. Ce module génère ces interfaces tout seul à partir des propriétés, méthodes et signaux de l'objet, et laisse ensuite choisir, sans code, quoi afficher et comment.

🪄 ProceduralEditor — l'interface

Un Control à poser n'importe où : il affiche un widget par membre de sa cible (case, curseur, couleur, liste, sous-ressource dépliable, bouton de méthode, liens de signaux…), avec annulation et suivi en direct.

🪟 ObjectEditorWindow — la fenêtre de debug

Une fenêtre unique, ouverte d'une ligne en jeu, et automatiquement dans l'éditeur à la sélection d'un objet qui a une interface de type.

🗂️ LayoutDatabase — interfaces par type

Une interface par classe (« tous les Ennemi ») : données, groupes, style, comportements conditionnels, gizmos et liens de signaux, enregistrée dans un .tres du projet.

🎯 GizmoHost — dessins automatiques

Rayon de détection, chemin, zone : des fonctions de Gizmos2D / Gizmos3D dont les paramètres suivent les propriétés de l'objet, dans l'éditeur et en jeu.

Pour qui ? Les développeurs qui veulent une console de debug sans écrire d'UI, les game designers qui configurent des interfaces dans l'éditeur (fenêtres « Configurer l'interface » et « Interfaces par type »), et les autres modules du toolkit qui ont besoin d'un panneau d'édition.

Ce que ce module n'est pas
  • Pas un remplaçant de l'inspecteur de Godot : il ne gère ni les ressources importées, ni les propriétés d'éditeur avancées (courbes, dégradés, animations). Il affiche ce qu'il sait représenter, le reste en lecture seule.
  • Pas les gizmos eux-mêmes : les fonctions de dessin viennent du module 🐛 Gizmos ; ce module ne fait que les appeler automatiquement.
  • Pas la fenêtre générique : 🪟 Fenêtre d'édition (WindowEditor) est une fenêtre vide réutilisable ; ObjectEditorWindow est spécialisée dans l'édition d'un objet.

Mise en place

  1. Compiler le module (si les binaires ne sont pas déjà présents) depuis la racine du dépôt : 
    scons tool_editor
    Le registre tool_editor_register.cpp donne l'identifiant tool_editor : seule cette bibliothèque est recompilée et son .gdextension régénéré.
  2. Copier le dossier bin/tool_editor/ dans le projet, à l'emplacement res://bin/tool_editor/.
    Le .gdextension référence ses binaires par des chemins res://bin/tool_editor/… absolus.
  3. Redémarrer l'éditeur après le premier ajout.
    Les extensions ne sont découvertes qu'au démarrage, et le plugin d'éditeur (bouton de l'inspecteur, menu Outils, ouverture automatique, plugin d'export) est installé à ce moment-là.
  4. Vérifier : Ajouter un nœud propose ProceduralEditor et GizmoHost ; le menu Projet › Outils contient « Éditeur d'objet : interfaces par type… ».
    Si ces entrées manquent, la bibliothèque n'est pas chargée : voir le panneau Sortie.
  5. (Optionnel) Réglages de projet gameplay_toolkit/object_editor/layout_database (chemin de la base) et gameplay_toolkit/object_editor/default_style (style par défaut) ; réglage d'éditeur gameplay_toolkit/object_editor/auto_open.
    Ils sont déclarés au chargement du module avec leur valeur par défaut, et ne sont écrits dans project.godot que si on les modifie.

Aucun autoload n'est requis : le LayoutLinker (liens par type en jeu) est créé par le module lui-même. À l'export, la base des interfaces et ses dépendances sont ajoutées automatiquement, même en export « ressources sélectionnées ».

⚙️ Mode d'emploi

A. Une fenêtre de debug en jeu, en une ligne

  1. Appeler ObjectEditorWindow.open_for() sur l'objet à inspecter, par exemple sur une touche : 
    func _unhandled_input(event: InputEvent) -> void:
	if event.is_action_pressed("debug_inspecter"):
		ObjectEditorWindow.open_for($Joueur)
    La fenêtre est créée sous la racine du jeu, lit les variables exportées du script (interface générale) et crée un widget par variable.
  2. Modifier une valeur dans la fenêtre : elle est appliquée immédiatement ; Ctrl+Z l'annule.
    Chaque édition est une action d'un historique propre au jeu (RuntimeUndoBackend) ; un glissement de curseur ne compte que pour une action.
  3. Laisser le jeu tourner : les valeurs modifiées par le jeu se mettent à jour dans la fenêtre (toutes les 0,1 s), même en pause.
    Le SyncController relit les widgets visibles ; un champ en cours de saisie n'est pas écrasé.

B. Une interface choisie dans l'éditeur (menu d'options, panneau de réglages)

  1. Ajouter un nœud ProceduralEditor dans un Control de la scène et régler target_path sur le nœud à éditer (ou target_resource sur un .tres).
    En jeu, la cible déclarée est appliquée au _ready ; dans l'éditeur, le nœud reste vide pour ne pas modifier la scène par accident.
  2. Cliquer sur « Configurer l'interface » en tête de l'inspecteur.
    La fenêtre liste les membres de la cible (onglet Données) avec un aperçu en direct ; le registre ainsi construit est enregistré avec la scène.
  3. Pour chaque donnée, choisir le widget (ex. HSlider pour un volume), décocher les données à masquer, puis ranger les données dans des Groupes.
    Seuls les widgets compatibles avec le type sont proposés ; les réglages (bornes, icône, style) se règlent sous le tableau.
  4. Lancer la scène : l'interface s'affiche telle que configurée.
    Si le script de la cible gagne une variable, elle apparaîtra automatiquement (widget Auto) ; une variable supprimée est marquée manquante, jamais effacée.

C. Une interface par type, ouverte automatiquement dans l'éditeur

  1. Ouvrir Projet › Outils › « Éditeur d'objet : interfaces par type… », puis « Créer » la base si elle n'existe pas.
    La base est le fichier désigné par le réglage gameplay_toolkit/object_editor/layout_database.
  2. Ajouter un type (ex. Ennemi, le class_name d'un script) et configurer ses onglets Données, Groupes, Gizmos, Style, Comportements ; « Enregistrer ».
    Les membres sont lus sur une instance d'exemple du type ; la base n'est écrite qu'au clic sur « Enregistrer ».
  3. Sélectionner un nœud Ennemi dans la scène : la fenêtre « Éditeur d'objet » s'ouvre avec son interface, et ses gizmos apparaissent dans la vue.
    Le plugin écoute la sélection ; tant que la fenêtre n'est pas épinglée, elle suit les objets sélectionnés. Les modifications rejoignent l'historique de l'éditeur.

💻 API Accessible

Référence générée depuis les doc_classes/*.xml des 64 classes, regroupées ci-dessous par sous-système. Éléments internes, non exposés (pas de XML, susceptibles de changer sans préavis) :

  • Classes internes du runtime : WidgetContext / ProceduralEditorContext (contexte de construction des widgets imbriqués), MaterialPropagator (propagation des matériaux), ArgumentStore (arguments d'un bouton de méthode), NodeSelectorDialog (sélecteur de nœud en jeu), et les classes C++ pures WidgetTable (widgets autorisés par type), TypeUtils, GizmoCatalog, BehaviorState.
  • Outils d'éditeur internes : ObjectEditorPlugin, ProceduralEditorInspectorPlugin, LayoutDatabaseExportPlugin, les fenêtres InterfaceConfigWindow et GizmoConfigWindow, le panneau ObjectInterfacePanel (ouvert par le bouton « Ouvrir fenêtre de personnalisation » de la barre d'outils, plugin EditorTest), et les éditeurs DataMatrixEditor, GroupMatrixEditor, GizmoListEditor, BehaviorListEditor, InterfaceStyleEditor, IconPickerRow.
  • Membres privés notables : les surcharges C++ build_editor / pull_value des widgets (équivalents de _build / _pull), setup() et set_context() de PropertyWidget (appelés par le ProceduralEditor), WidgetFactory::create, ProceduralEditor::build_widget.
  • PropertyBoolCallback et WidgetPropertyModifierBuilder ont encore un XML mais leur code source n'existe plus (ancienne version, absente de bin/tool_editor) : ils ne sont pas documentés ici.

Construction de l'interface

Le point d'entrée : ProceduralEditor (l'interface) et ObjectEditorWindow (la fenêtre unique). La WidgetFactory choisit les widgets ; le SyncController et la RichTooltip sont des nœuds internes de chaque éditeur.

Données et registres

Ce qui est affiché : un DataRegistry (une DataEntry par membre) et un GroupRegistry. Rangés par type dans une LayoutDatabase (un TypeLayout par classe) ; le LayoutLinker applique en jeu les liens de signaux de ces interfaces.

Sources de valeurs et liens de signaux

ArgumentBinding décrit d'où vient une valeur (constante, propriété, fonction, argument de signal) ; il sert aux liens SignalLink, aux gizmos, aux conditions des comportements, aux uniforms des styles et aux sources des aperçus.

Comportements conditionnels

Rangés dans DataRegistry.behaviors : montrer, cacher, verrouiller, styler, compléter l'infobulle ou changer l'icône de données et de groupes selon une condition lue sur l'objet. Un script peut créer les siens en surchargeant _apply.

Réglages des widgets et styles

Une ressource de réglages typée par widget (plus de dictionnaire à clés libres), et des InterfaceStyle applicables à l'interface entière, à un groupe ou à un widget.

Widgets

PropertyWidget est la base de tous les widgets et le point d'extension des widgets personnalisés (_build, _pull). Les classes dérivées sont créées par la fabrique ; elles n'ajoutent rien à l'API exposée mais sont listées pour leur description.

Aperçus

Des entrées « aperçu » qui n'éditent rien mais montrent une image, un modèle ou une scène liés à l'objet, dans des scènes isolées. Point d'extension : PreviewWidget.

Gizmos automatiques

Annulation et accès aux valeurs

Toute écriture d'un widget passe par un ValueAccessor (valeur éventuellement imbriquée) et un UndoBackend (une action par édition).

Outils d'éditeur accessibles aux scripts

Classes enregistrées au niveau éditeur (absentes d'un jeu exporté) et non instanciables, exposées pour les scripts d'éditeur et les tests.

Démonstration

📌 Exemples d'utilisation

Comment j'intègre un éditeur dans mon propre panneau de debug ?

Le ProceduralEditor est un VBoxContainer ordinaire. clear_registries() avant chaque set_target : sinon, après une cible sans interface de type, le registre automatique est réutilisé pour les suivantes.

@onready var editeur: ProceduralEditor = $Panneau/ProceduralEditor

func inspecter(objet: Object) -> void:
	editeur.clear_registries()   # chaque objet reprend l'interface de son type
	editeur.set_target(objet)
	$Panneau/Titre.text = objet.get_class()

func _on_bouton_annuler_pressed() -> void:
	editeur.undo()

Comment je choisis par code les données et leurs widgets ?

func _ready() -> void:
	var registre := DataRegistry.new()
	registre.scan_methods = true          # boutons pour les méthodes publiques
	registre.sync($Joueur)                # une entrée par membre

	var vitesse := registre.find(&"vitesse")
	vitesse.widget_choice = DataEntry.WIDGET_H_SLIDER
	var bornes := RangeWidgetSettings.new()
	bornes.max_value = 20.0
	bornes.suffix = " m/s"
	vitesse.settings = bornes

	registre.find(&"secret").enabled = false   # masquée, configuration conservée

	$ProceduralEditor.registry = registre
	$ProceduralEditor.set_target($Joueur)

Comment je range les données en sections et en onglets ?

var groupes := GroupRegistry.new()
var stats := groupes.ensure("Stats")
stats.container_type = GroupEntry.CONTAINER_GRID
stats.columns = 2
for nom in ["vie", "force", "agilite", "chance"]:
	groupes.assign(nom, stats)
groupes.assign("arme", groupes.ensure("Équipement"))

var fiche := groupes.ensure("Fiche")
fiche.container_type = GroupEntry.CONTAINER_TABS
fiche.child_groups = PackedStringArray(["Stats", "Équipement"])  # un onglet par groupe

$ProceduralEditor.group_registry = groupes

Comment je cache ou verrouille un champ selon l'état de l'objet ?

Attention : un comportement dont la condition n'est pas réglée vaut faux (un « Montrer si » vide masque donc sa cible).

var registre: DataRegistry = $ProceduralEditor.get_active_registry()

var cacher := HideIfBehavior.new()
cacher.get_condition().property_path = ^"est_mort"
cacher.targets = PackedStringArray(["vie", "Stats"])   # une donnée et un groupe

var activer := EnableIfBehavior.new()
activer.get_condition().property_path = ^"utilise_physique"
activer.targets = PackedStringArray(["masse"])         # lecture seule si faux

var aide := TooltipIfBehavior.new()
aide.get_condition().property_path = ^"surcharge"
aide.tooltip = "[color=orange]Surcharge :[/color] {poids} / {poids_max} kg"
aide.targets = PackedStringArray(["poids"])

registre.behaviors = [cacher, activer, aide]
$ProceduralEditor.rebuild()

Comment je crée mon propre widget ?

Un script avec class_name qui hérite de PropertyWidget : _build construit le contrôle, _pull affiche la valeur, emit_value transmet la saisie. Il est choisi par DataEntry.WIDGET_CUSTOM + custom_widget_class, ou pour tout un choix via WidgetFactory.set_widget_class.

class_name CurseurEtoiles
extends PropertyWidget

var _etoiles: HBoxContainer

func _build(info: Dictionary, settings: WidgetSettings) -> Control:
	_etoiles = HBoxContainer.new()
	for i in 5:
		var b := Button.new()
		b.text = "☆"
		b.pressed.connect(func(): emit_value(i + 1, true))  # true : modification validée
		_etoiles.add_child(b)
	return _etoiles

func _pull(value: Variant) -> void:
	for i in 5:
		_etoiles.get_child(i).text = "★" if i < int(value) else "☆"

Comment je relie un signal à une méthode sans code de connexion ?

En jeu, un lien « mode ressource » passe des arguments arbitraires : argument du signal, propriété de l'émetteur ou constante. Rangé dans l'interface du type, il est appliqué automatiquement à tout nœud de ce type par le LayoutLinker.

var lien := SignalLink.new()
lien.target_path = ^"../HUD"
lien.method = &"afficher_degats"
var degats := ArgumentBinding.new()
degats.source = ArgumentBinding.SOURCE_SIGNAL_ARG
degats.signal_index = 0
var position := ArgumentBinding.new()
position.source = ArgumentBinding.SOURCE_PROPERTY
position.property_path = ^"global_position"   # lue sur l'émetteur
lien.arguments = [degats, position]

var base := LayoutDatabase.load_project_database()
var interface := base.ensure_type("Ennemi")
interface.data_registry.scan_signals = true
var modele := Ennemi.new()               # instance d'exemple pour lire les membres
interface.data_registry.sync(modele)
modele.free()
interface.data_registry.find(&"touche", DataEntry.MEMBER_SIGNAL).links = [lien]
ResourceSaver.save(base, LayoutDatabase.get_project_path())

Comment je dessine le rayon de détection d'un ennemi, dans l'éditeur et en jeu ?

# Enfant d'un Node2D qui exporte « rayon_detection ».
func _ready() -> void:
	var cercle := GizmoEntry.new()
	cercle.function = "Gizmos2D.draw_2D_circle"     # crée les arguments par défaut
	cercle.arguments[1].source = ArgumentBinding.SOURCE_PROPERTY
	cercle.arguments[1].property_path = ^"rayon_detection"  # radius
	cercle.arguments[2].constant = Color.ORANGE            # color
	var registre := GizmoRegistry.new()
	registre.entries = [cercle]
	var hote := GizmoHost.new()
	hote.registry = registre
	add_child(hote)   # cible et viewport : ceux du parent

Comment je modifie une valeur imbriquée de façon annulable depuis mon propre outil ?

var annulation := RuntimeUndoBackend.new()

func deplacer_point(chemin: Path3D, index: int, point: Vector3) -> void:
	var acces := ValueAccessor.new()
	acces.setup(chemin, &"points_patrouille")            # PackedVector3Array exporté
	var element := acces.child(index, {"type": TYPE_VECTOR3}, "[%d]" % index)
	annulation.edit_property(element, point, true)        # une action « ancien → nouveau »

func _on_annuler() -> void:
	annulation.undo()

🚧 Limitations

Interface et synchronisation

  • Un éditeur réutilisé garde son registre automatique. Après set_target sur un objet sans interface de type, le registre créé est conservé : les cibles suivantes l'utilisent (même si elles ont une interface de type), et les membres de l'ancienne cible y restent marqués manquants. Appeler clear_registries() avant chaque changement de type (ObjectEditorWindow le fait).
  • Suivi par relecture périodique. Toutes les 0,1 s par défaut, chaque widget visible est relu (get() + comparaison) : coût proportionnel au nombre de widgets visibles. Les widgets masqués (section repliée, comportement « Cacher si ») ne sont plus mis à jour.
  • Ressources partagées. Éditer une sous-ressource partagée modifie toutes ses utilisatrices ; rien ne le signale.
  • Structures en composantes brutes. Quaternion en x/y/z/w, Transform3D en 9 coefficients + origine : pas d'angles en degrés ni d'échelle. Le mode « canaux » des couleurs est borné à 0-1 (pas de HDR).
  • Pas d'équivalent des éditeurs spécialisés de l'inspecteur (Curve, Gradient, animation…) : ces ressources sont dépliées propriété par propriété.
  • Les boutons de méthode appellent vraiment la méthode, hors historique d'annulation, y compris dans l'éditeur (sur un script non @tool, l'appel échoue).
  • open_for réutilise la fenêtre telle quelle : le paramètre backend n'est pris en compte qu'à sa création.
  • Une interface en jeu ne se branche qu'au _ready : changer target_path ensuite n'a pas d'effet sans set_target.

Annulation

  • Fusion des modifications rapprochées. En jeu, deux modifications de la même propriété à moins de 0,8 s d'intervalle forment une seule action (MERGE_ENDS) : un seul Ctrl+Z annule les deux (vérifié en test).
  • L'annulation porte sur la propriété racine : changer un élément d'un tableau de 10 000 éléments enregistre deux copies complètes du tableau.
  • Dans l'éditeur, annuler / rétablir simule Ctrl+Z / Ctrl+Maj+Z : si ces raccourcis ont été changés dans l'éditeur, les boutons et raccourcis de la fenêtre n'agissent plus.

Registres, interfaces par type et liens

  • Les entrées manquantes ne sont jamais supprimées automatiquement : une propriété renommée laisse une entrée orpheline (à retirer dans la fenêtre de configuration).
  • Un script sans class_name compte comme sa classe native : une interface Node sans « inclure les sous-classes » s'applique quand même à un nœud scripté anonyme.
  • Liens en mode ressource : en jeu seulement. Ils ne sont appliqués que par le LayoutLinker (nœuds dont le type a une interface dans la base du projet, chargée une seule fois au démarrage) ou par un ProceduralEditor ouvert. Une ressource n'a aucun déclencheur automatique. Les liens d'un registre automatique (non enregistré) sont perdus.
  • Liens natifs (éditeur) : seule la correspondance « les k premiers paramètres = les k premiers arguments du signal » est possible (contrainte de bind / unbind).
  • Lecture des membres d'un type sur une instance d'exemple (fenêtre « Interfaces par type ») : un type abstrait, ou un script dont _init exige des arguments, ne peut pas être lu ; un _init à effets de bord s'exécute.
  • Condition non réglée = faux : un « Montrer si » ajouté sans condition masque sa cible.

Aperçus, gizmos et icônes

  • Aperçu reconstruit seulement si la source change d'identité : une ressource modifiée en interne (même objet) n'est pas rafraîchie en mode « Au changement ».
  • Copies de nœuds sans scripts par défaut : un personnage animé par script reste figé dans l'aperçu (sauf duplicate_scripts, qui exécute alors sa logique).
  • Gizmos « Sur changement » : les arguments sont résolus et comparés à chaque image, même sans redessin.
  • Icônes de l'éditeur copiées aux couleurs du thème courant de l'éditeur (claires sur thème sombre).

🏗️ Architecture

Composants et communication

  • Résolution de l'interface : ProceduralEditor.set_target prend ses registres propres, sinon le TypeLayout de la cible (LayoutDatabase.find_layout), sinon un registre automatique ; puis DataRegistry.sync fusionne les membres de la cible avec les entrées.
  • Construction : pour chaque entrée, la WidgetFactory instancie un PropertyWidget ; l'éditeur le configure (setup, réglages, styles), le place dans son groupe et l'enregistre auprès du SyncController. Les widgets qui en contiennent d'autres (collections, objets, Variant, méthodes) passent par un WidgetContext qui rappelle l'éditeur : profondeur et anti-cycle centralisés.
  • Écriture (appels directs + signal) : le widget émet value_changed(valeur, committing) → l'éditeur appelle UndoBackend.edit_property → ValueAccessor.write reconstruit la racine et fait un set() → SyncController.notify_written relit et corrige le widget si le setter a transformé la valeur.
  • Lecture : le SyncController (nœud interne, _process) relit les widgets visibles et appelle pull() ; il émet synced, sur lequel l'éditeur réévalue les comportements, et target_lost quand la cible est libérée.
  • Gizmos : un GizmoHost (nœud de scène, ou interne à l'éditeur pour le type de la cible) appelle les fonctions statiques draw_* de Gizmos2D/Gizmos3D via ClassDB.class_call_static.
  • Éditeur Godot : ObjectEditorPlugin écoute EditorSelection.selection_changed et l'objet de l'inspecteur (différé), ouvre ou fait suivre l'ObjectEditorWindow ; l'inspector plugin ajoute « Configurer l'interface / les gizmos » ; l'export plugin ajoute la base. Jeu : le singleton LayoutLinker écoute SceneTree.node_added.

Dépendances et couplage

  • Dépend de 🐛 Gizmos (Gizmos2D, Gizmos3D, Gizmos) et de 📰 Journal Console (log_it), tous compilés dans la même bibliothèque tool_editor. Le catalogue des fonctions de dessin est lu dans ClassDB : aucune liste en dur, une nouvelle fonction draw_* apparaît automatiquement.
  • Runtime enregistré au niveau SCENE, outils d'éditeur au niveau EDITOR (fichiers séparés) ; le code runtime n'appelle une API d'éditeur que derrière is_editor_hint() et un test du singleton.
  • Les autres modules n'incluent pas ses en-têtes : ils passent par Godot (ObjectEditorWindow.open_for(obj), ClassDB.instantiate("ProceduralEditor")).

Décisions de conception

ChoixPourquoi (ne pas « corriger » sans en tenir compte)
Un seul SyncController par éditeur, relecture des widgets visibles seulementGodot n'a aucun signal « valeur modifiée ». La version C# d'origine avait un nœud de polling par widget, trop coûteux ; un intervalle configurable et l'exclusion des widgets masqués bornent le coût.
Un widget n'écrit jamais dans l'objetToutes les écritures passent par l'UndoBackend : une seule action par édition, en jeu comme dans l'éditeur, sans dupliquer la logique dans chaque widget.
ValueAccessor réécrit toujours la propriété racine (copie à chaque niveau)Packed*Array, vecteurs, transformations sont copiés à la lecture : modifier une copie ne change rien. Réécrire la racine garantit aussi que le setter est appelé et que l'annulation porte sur une seule propriété.
Relecture après écriture (notify_written)Un setter peut borner ou refuser une valeur ; sans relecture, le widget afficherait une valeur fausse.
Entrées manquantes jamais suppriméesUn renommage temporaire, ou une cible d'un autre sous-type, ne doit pas effacer une configuration soignée.
Réglages typés (WidgetSettings et sous-classes) au lieu d'un dictionnaireFautes de frappe impossibles, valeurs validées par l'inspecteur (c'était le principal défaut de l'ExtraData du C#).
Valeurs des énumérations explicites, jamais renumérotéesElles sont enregistrées comme entiers dans les .tres : renuméroter casserait toutes les interfaces existantes.
Objets désignés par ObjectID, jamais par pointeurLa cible peut être libérée à tout moment (ennemi détruit) : l'interface affiche « Objet libéré » au lieu de planter.
Deux modes de liens de signauxLe mode natif (CONNECT_PERSIST) s'intègre à la scène et à l'onglet Nœud, mais bind/unbind limitent la correspondance ; le mode ressource (Callable personnalisé) permet tout, au prix d'une application à l'exécution.
LayoutLinker créé hors de l'éditeur seulementDans l'éditeur, aucun lien ne doit déclencher de logique de jeu sur la scène éditée.
GizmoHost seul propriétaire des RID, 1 RID par formeChaque draw_* efface son gizmo avant de dessiner ; un propriétaire unique qui libère tout à la sortie de l'arbre évite les fuites de ressources du RenderingServer.
Contenu des conteneurs construit à l'ouverture, reconstruit seulement si la structure changeUn gros tableau ou une ressource profonde ne coûte rien tant qu'il est replié, et une valeur qui change ne détruit pas les widgets (ni le focus).
Icônes de l'éditeur copiées dans res://object_editor_icons/Les icônes de l'éditeur n'existent pas dans un jeu exporté.
