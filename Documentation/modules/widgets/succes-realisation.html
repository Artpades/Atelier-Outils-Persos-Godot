🏆_AchievementSystem - Widgets & Spatialité - Documentation

Module Succès - Réalisation : définir des succès dans l'inspecteur, les faire progresser par des évènements de jeu, les sauvegarder et les annoncer à l'écran.

Godot 4.7+ Bibliothèque bin/achievements 5 classes Inspiré de Terraria / tModLoader

📝 Présentation

« Tuer 100 slimes », « ramasser chaque gemme », « finir le jeu sans mourir », « débloquer tous les autres succès » : écrits à la main, les succès finissent en compteurs dispersés dans tout le code, couplés à chaque système du jeu, et à sauvegarder séparément. Ce module sépare les deux mondes : le jeu se contente d'annoncer ce qui se passe (notify(&"enemy_killed", "slime")), et chaque succès, décrit dans une ressource, décide si l'évènement le concerne. Progression, sauvegarde, notification à l'écran et son sont gérés.

🏆 AchievementManager

Le nœud (en autoload) qui reçoit les évènements, les transmet, sauvegarde et affiche les notifications.

🎖️ Achievement

Une ressource par succès : nom, description, icônes, catégorie, conditions et mode de complétion.

🚩 Conditions

AchievementCondition (drapeau), AchievementCounterCondition (compteur, record, état) et AchievementCollectionCondition (liste à compléter) ; extensibles par script.

Pour qui ? Les game designers qui définissent les succès dans l'inspecteur, et les développeurs qui n'ont qu'une ligne à ajouter là où les choses se passent.

Ce que ce module n'est pas
  • Pas une intégration Steam / consoles : il n'appelle aucune plateforme, mais son signal achievement_unlocked sert de point de branchement.
  • Pas un menu des succès : seule la notification « Succès débloqué ! » est fournie ; la liste (icônes, progression, catégories) est à construire avec l'API.
  • Pas le système de sauvegarde du jeu : il a son propre fichier, ou s'intègre au 💾 Système de Sauvegarde par get_state / set_state.

Mise en place

  1. Compiler (si besoin) : 
    scons achievements
    compile la bibliothèque du registre achievements_register.cpp.
  2. Copier bin/achievements/ dans res://bin/ et redémarrer l'éditeur.
    chemins res://bin/achievements/… absolus ; extensions découvertes au démarrage.
  3. Créer une scène succes.tscn dont la racine est un AchievementManager, et la déclarer en autoload sous le nom Achievements.
    le gestionnaire n'est pas un singleton automatique : en autoload, il survit aux changements de scène et reste accessible partout ; sa sauvegarde est rechargée une seule fois.

⚙️ Mode d'emploi

Objectif : un succès « Tueur de slimes » débloqué au 10e slime tué.

  1. Dans achievements du gestionnaire, ajouter un Nouveau Achievement : id = slime_slayer, display_name = « Tueur de slimes », une icon.
    l'id identifie le succès dans le code et dans la sauvegarde : ne plus le changer une fois le jeu publié.
  2. Dans ses conditions, ajouter une Nouvelle AchievementCounterCondition : event_name = enemy_killed, event_ids = ["slime"], target = 10.
    la condition n'écoute que les évènements enemy_killed d'identifiant slime et ajoute leur quantité (1 par défaut) au compteur.
  3. Annoncer l'évènement là où l'ennemi meurt : 
    func mourir() -> void:
	Achievements.notify(&"enemy_killed", type_id)   # type_id = "slime"
	queue_free()
    le code de l'ennemi ignore tout des succès : il décrit seulement ce qui s'est passé.
  4. Lancer et tuer 10 slimes : la notification apparaît, et la progression est sauvegardée dans user://achievements.cfg.
    auto_save sauvegarde à chaque déblocage et à la sortie de l'arbre ; auto_load recharge au lancement suivant.

💻 API Accessible

Référence générée depuis doc_classes/AchievementManager.xml, Achievement.xml, AchievementCondition.xml, AchievementCounterCondition.xml et AchievementCollectionCondition.xml. Éléments internes, non exposés : le calque de notifications (CanvasLayer interne de couche 100) et le lecteur audio interne du gestionnaire, les listes de connexions aux signaux (connected_achievements, connected_conditions), l'indicateur updating qui évite les réévaluations pendant unlock() / reset(), et les méthodes protégées _apply_event, _set_completed. La méthode virtuelle _handle_event est, elle, documentée : elle est faite pour être surchargée.

📌 Exemples d'utilisation

Comment je fais « ramasser chaque gemme » ?

Une AchievementCollectionCondition retient les identifiants reçus ; elle est remplie quand tous ceux de required_ids ont été vus.

var gemmes := AchievementCollectionCondition.new()
gemmes.event_name = &"item_collected"
gemmes.required_ids = PackedStringArray(["rubis", "saphir", "emeraude", "topaze"])
var succes := Achievement.new()
succes.id = &"collectionneur"
succes.display_name = "Collectionneur"
succes.add_condition(gemmes)
Achievements.register_achievement(succes)

# Ailleurs, à chaque ramassage :
Achievements.notify(&"item_collected", "saphir")

Comment je fais un succès de record (score, altitude) ?

VALUE_MODE_MAX garde la plus grande quantité reçue.

# Condition : event_name = "altitude", target = 500, value_mode = Max
func _physics_process(_delta: float) -> void:
	Achievements.notify(&"altitude", "", -global_position.y)

Comment je fais « débloquer 10 succès » ou « débloquer A, B et C » ?

Le gestionnaire émet lui-même l'évènement achievement_unlocked (identifiant = id du succès) à chaque déblocage.

var compteur := AchievementCounterCondition.new()
compteur.event_name = &"achievement_unlocked"   # n'importe quel succès
compteur.target = 10
var platine := Achievement.new()
platine.id = &"platine"
platine.add_condition(compteur)
Achievements.register_achievement(platine)

Comment j'écris une condition personnalisée ?

Surcharger _handle_event : la condition décide seule si l'évènement la concerne, et appelle complete().

# sans_degats.gd
extends AchievementCondition

var degats_recus := false

func _handle_event(event: StringName, id: String, amount: float) -> bool:
	if event == &"player_hurt":
		degats_recus = true
		return true
	if event == &"boss_defeated" and not degats_recus:
		complete()
		return true
	return false

Les variables d'un script de condition (degats_recus ici) ne sont pas sauvegardées : seul l'état « rempli » l'est. Surcharger aussi get_state / set_state si nécessaire.

Comment je relaie les succès vers Steam ou une autre plateforme ?

func _ready() -> void:
	Achievements.achievement_unlocked.connect(func(succes: Achievement):
		Steam.setAchievement(String(succes.id))
		Steam.storeStats())

Comment j'affiche la liste des succès avec leur progression ?

func remplir_menu() -> void:
	for succes: Achievement in Achievements.achievements:
		var ligne := preload("res://ui/ligne_succes.tscn").instantiate()
		ligne.get_node("Icone").texture = succes.get_current_icon()
		if succes.is_hidden() and not succes.is_unlocked():
			ligne.get_node("Nom").text = "???"
		else:
			ligne.get_node("Nom").text = succes.display_name
		ligne.get_node("Barre").visible = succes.has_progress()
		ligne.get_node("Barre").value = succes.get_progress() * 100
		ligne.get_node("Texte").text = succes.get_progress_text()
		$Liste.add_child(ligne)

Comment j'intègre les succès à ma propre sauvegarde ?

# Dans l'inspecteur : auto_load = false, auto_save = false
func sauvegarder(donnees: Dictionary) -> void:
	donnees["succes"] = Achievements.get_state()

func charger(donnees: Dictionary) -> void:
	Achievements.set_state(donnees.get("succes", {}))   # aucun signal, aucune notification

🚧 Limitations

  • L'état vit dans les ressources : un Achievement chargé depuis un .tres est partagé par le cache de ressources. Deux gestionnaires qui utilisent les mêmes fichiers partagent la progression ; une scène qui recharge le .tres voit l'état en cours, pas l'état du fichier. Un seul gestionnaire, en autoload.
  • Identifiants en double non détectés dans l'inspecteur : seul register_achievement refuse un id déjà pris ; dans le tableau achievements, le premier l'emporte pour get_achievement, et la sauvegarde mélange les deux.
  • Identifiants comparés comme texte : notify(e, 1.0) envoie "1.0", qui ne correspond pas à event_ids = ["1"]. Envoyer des chaînes ou des StringName.
  • Notification et son suivent la pause : le Tween de la notification et le lecteur audio appartiennent au gestionnaire ; un succès débloqué pendant la pause reste affiché jusqu'à la reprise. Régler process_mode = ALWAYS sur l'autoload si nécessaire.
  • Notifications empilées sans limite, au style fixe (bordure dorée, police par défaut) ; pour un autre style, désactiver show_notifications et utiliser achievement_unlocked, ou modifier get_notification_container().
  • Sauvegarde synchrone à chaque déblocage : une écriture de fichier sur le fil principal (négligeable sauf sur des supports lents).
  • Conditions irréversibles : une condition remplie le reste, même si un compteur VALUE_MODE_SET redescend ; seul reset() l'annule.
  • Sauvegarde par nom de condition : une condition sans condition_name est sauvegardée par son rang ; réordonner les conditions après publication mélange leur progression. Toujours nommer les conditions.
  • Rien dans l'éditeur : ni notification ni lecture / écriture de sauvegarde quand le gestionnaire est édité.

🏗️ Architecture

Composants et communication

  • Descente (appels directs) : AchievementManager.notify → Achievement.notify de chaque succès verrouillé → AchievementCondition.notify de chaque condition non remplie, qui teste matches (ou délègue au script par _handle_event) puis applique l'évènement.
  • Remontée (signaux) : une condition qui change émet changed ; le succès se réévalue et émet progressed ou unlocked ; le gestionnaire, connecté à chaque succès, émet ses propres signaux, affiche la notification, sauvegarde, puis réinjecte l'évènement achievement_unlocked pour les méta-succès.
  • Sauvegarde : get_state / set_state descendent la même hiérarchie ; le gestionnaire les écrit en ConfigFile (une section par succès). Le chargement n'émet aucun signal.

Dépendances et couplage

  • Le jeu ne dépend que d'un nom d'évènement et d'un identifiant : aucun couplage entre le code de gameplay et les succès.
  • Hiérarchie interne : AchievementCounterCondition et AchievementCollectionCondition héritent d'AchievementCondition.
  • Aucune dépendance vers d'autres modules. Bibliothèque propre : achievements_register.cpp → bin/achievements/.

Décisions de conception

ChoixPourquoi (ne pas « corriger » sans en tenir compte)
Évènements génériques (nom + identifiant + quantité), comme TerrariaAjouter un succès ne demande aucune modification du code de jeu ; un même évènement nourrit plusieurs succès.
Déblocage réinjecté comme évènementLes méta-succès (« débloquer N succès ») se construisent avec les conditions existantes, sans cas particulier.
État de jeu jamais enregistré dans la ressource (value en PROPERTY_USAGE_EDITOR, pas de propriété unlocked)Sauvegarder la scène dans l'éditeur ne doit pas écrire la progression d'une partie de test dans le .tres. Une propriété unlocked masquerait en plus le signal du même nom en GDScript.
set_state sans signalRecharger une sauvegarde ne doit pas réafficher toutes les notifications ni redéclencher Steam.
Indicateur updating pendant unlock() / reset()Remplir les conditions une à une provoquerait plusieurs réévaluations et des signaux intermédiaires.
Notification construite en code, en enfant interneFonctionne sans aucune scène d'interface à fournir ; non sauvegardée avec l'autoload.
ConfigFile lisible, chiffrement facultatifFacile à déboguer en développement ; save_password décourage la triche en production.
